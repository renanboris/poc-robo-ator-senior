# Requirements Document

## Introduction

The Web Knowledge Ingestion Pipeline (RAG) replaces the manual PDF reading workflow with an automated web extraction engine. The system discovers documentation URLs from sitemap.xml, extracts clean semantic content converted to Markdown, structures data with breadcrumb hierarchy, and injects vectors into Pinecone segregated by namespaces. This enables the Training OS platform to retrieve relevant documentation context during Aura DAP interactions and training generation workflows.

## Glossary

- **Pipeline**: The Web Knowledge Ingestion Pipeline system
- **Sitemap_Crawler**: Component responsible for reading and parsing sitemap.xml files
- **Semantic_Extractor**: Component that converts HTML pages to clean Markdown using Crawl4AI or Firecrawl API
- **Chunker**: Component that splits Markdown content into semantic chunks using LangChain
- **Vector_Injector**: Component that generates embeddings and upserts vectors to Pinecone
- **Breadcrumb**: Navigation hierarchy extracted from URL structure (e.g., /senior-x/hcm/admissao → nivel_1: senior-x, nivel_2: hcm, nivel_3: admissao)
- **Namespace**: Pinecone namespace derived from nivel_2 (module name) used to segregate vectors by documentation module
- **Chunk**: A semantic segment of documentation content, approximately 800 tokens with 100 token overlap
- **Embedding**: Vector representation of text generated by OpenAI text-embedding-3-large model
- **Metadata_Payload**: Structured data attached to each vector containing url, nivel_1, nivel_2, titulo, and text fields
- **Training_OS**: The existing Senior Training OS platform that will consume the ingested vectors
- **Aura_DAP**: The existing Digital Adoption Platform engine (dap_engine.py) that retrieves vectors during user interactions
- **Senior_Documentation_Portal**: The public documentation website at Senior that serves as the source of knowledge

## Requirements

### Requirement 1: Sitemap Discovery

**User Story:** As a knowledge engineer, I want the system to automatically discover documentation URLs from sitemap.xml, so that I don't need to manually maintain URL lists.

#### Acceptance Criteria

1. WHEN a sitemap.xml URL is provided, THE Sitemap_Crawler SHALL fetch and parse the XML document
2. WHEN the sitemap.xml is parsed, THE Sitemap_Crawler SHALL extract all valid documentation URLs
3. THE Sitemap_Crawler SHALL filter out non-documentation pages (Terms of Use, Home, Privacy Policy, Contact)
4. WHEN URL filtering is applied, THE Sitemap_Crawler SHALL preserve URLs matching the pattern `/senior-x/*` or `/produto/*`
5. THE Sitemap_Crawler SHALL return a list of valid URLs for downstream processing

### Requirement 2: Semantic Content Extraction

**User Story:** As a knowledge engineer, I want the system to extract only the main article content as Markdown, so that navigation menus and footers don't pollute the knowledge base.

#### Acceptance Criteria

1. WHEN a documentation URL is processed, THE Semantic_Extractor SHALL fetch the page using Crawl4AI or Firecrawl API
2. THE Semantic_Extractor SHALL ignore navigation menus, footers, modals, and sidebar elements
3. THE Semantic_Extractor SHALL convert the main article content to Markdown format
4. WHEN content is extracted, THE Semantic_Extractor SHALL preserve semantic structure including headings, lists, and code blocks
5. THE Semantic_Extractor SHALL extract the page title from the HTML title tag or main heading

### Requirement 3: Breadcrumb Hierarchy Extraction

**User Story:** As a knowledge engineer, I want the system to extract breadcrumb hierarchy from URLs, so that vectors can be filtered by documentation module during retrieval.

#### Acceptance Criteria

1. WHEN a URL is processed, THE Semantic_Extractor SHALL parse the URL path to extract hierarchy levels
2. WHEN the URL matches the pattern `/nivel_1/nivel_2/nivel_3`, THE Semantic_Extractor SHALL extract nivel_1, nivel_2, and nivel_3 as separate metadata fields
3. WHEN the URL has fewer than 3 hierarchy levels, THE Semantic_Extractor SHALL populate available levels and leave others empty
4. THE Semantic_Extractor SHALL normalize hierarchy level values to lowercase kebab-case format
5. WHEN hierarchy extraction is complete, THE Semantic_Extractor SHALL include nivel_1, nivel_2, and titulo in the metadata payload

### Requirement 4: Semantic Chunking

**User Story:** As a knowledge engineer, I want documentation content split into semantic chunks, so that retrieval returns focused context rather than entire documents.

#### Acceptance Criteria

1. WHEN Markdown content is received, THE Chunker SHALL split the content using MarkdownHeaderTextSplitter or RecursiveCharacterTextSplitter from LangChain
2. THE Chunker SHALL configure chunk size to approximately 800 tokens
3. THE Chunker SHALL configure chunk overlap to approximately 100 tokens
4. THE Chunker SHALL preserve semantic boundaries by respecting Markdown headers and list structures
5. WHEN chunking is complete, THE Chunker SHALL return a list of text chunks with preserved context

### Requirement 5: Embedding Generation

**User Story:** As a knowledge engineer, I want text chunks converted to vector embeddings, so that semantic similarity search can retrieve relevant documentation.

#### Acceptance Criteria

1. WHEN a text chunk is received, THE Vector_Injector SHALL generate an embedding using OpenAI text-embedding-3-large model
2. THE Vector_Injector SHALL configure the embedding dimension to 3072
3. WHEN embedding generation fails, THE Vector_Injector SHALL retry up to 3 times with exponential backoff
4. THE Vector_Injector SHALL log embedding generation failures with the chunk text preview
5. WHEN embedding is generated successfully, THE Vector_Injector SHALL return a 3072-dimensional float vector

### Requirement 6: Vector Injection with Namespace Segregation

**User Story:** As a knowledge engineer, I want vectors injected into Pinecone with namespace segregation by module, so that retrieval can be scoped to relevant documentation sections.

#### Acceptance Criteria

1. WHEN a vector is ready for injection, THE Vector_Injector SHALL derive the namespace from the nivel_2 metadata field
2. THE Vector_Injector SHALL construct a unique vector ID using the format `{nivel_2}_{titulo_sanitized}_{chunk_index}`
3. THE Vector_Injector SHALL construct the metadata payload with fields: url, nivel_1, nivel_2, titulo, text
4. WHEN the vector is constructed, THE Vector_Injector SHALL upsert the vector to Pinecone using the derived namespace
5. WHEN upsert fails, THE Vector_Injector SHALL retry up to 3 times with exponential backoff
6. THE Vector_Injector SHALL log successful upserts with namespace and vector ID

### Requirement 7: Aura DAP Integration

**User Story:** As a Training OS developer, I want the Aura DAP engine to query vectors using namespace filtering, so that retrieval returns documentation relevant to the user's current module context.

#### Acceptance Criteria

1. WHEN Aura DAP performs a retrieval query, THE Aura_DAP SHALL accept a namespace parameter derived from the user's current module context
2. WHEN the namespace parameter is provided, THE Aura_DAP SHALL pass the namespace to the Pinecone query operation
3. WHEN the namespace parameter is not provided, THE Aura_DAP SHALL query the default namespace "senior_default"
4. THE Aura_DAP SHALL preserve existing retrieval logic for score thresholding and top-k selection
5. WHEN retrieval results are returned, THE Aura_DAP SHALL include the source URL from metadata in the response context

### Requirement 8: Pipeline Orchestration

**User Story:** As a knowledge engineer, I want to execute the entire ingestion pipeline with a single command, so that I can refresh the knowledge base efficiently.

#### Acceptance Criteria

1. THE Pipeline SHALL provide a command-line interface accepting a sitemap URL as input
2. WHEN the pipeline is executed, THE Pipeline SHALL execute stages in order: discovery, extraction, chunking, embedding, injection
3. THE Pipeline SHALL log progress for each stage with counts of processed items
4. WHEN a stage fails, THE Pipeline SHALL log the error and continue processing remaining URLs
5. WHEN the pipeline completes, THE Pipeline SHALL report total URLs processed, total chunks created, and total vectors injected

### Requirement 9: Configuration Management

**User Story:** As a knowledge engineer, I want pipeline configuration stored in environment variables, so that I can deploy to different environments without code changes.

#### Acceptance Criteria

1. THE Pipeline SHALL read the OpenAI API key from the environment variable `OPENAI_API_KEY`
2. THE Pipeline SHALL read the Pinecone API key from the environment variable `PINECONE_API_KEY`
3. THE Pipeline SHALL read the Pinecone index name from the environment variable `PINECONE_INDEX_NAME`
4. WHERE Crawl4AI is used, THE Pipeline SHALL read configuration from environment variables prefixed with `CRAWL4AI_`
5. WHERE Firecrawl API is used, THE Pipeline SHALL read the API key from the environment variable `FIRECRAWL_API_KEY`
6. WHEN a required environment variable is missing, THE Pipeline SHALL log a descriptive error and exit with a non-zero status code

### Requirement 10: Error Handling and Resilience

**User Story:** As a knowledge engineer, I want the pipeline to handle transient failures gracefully, so that a single page error doesn't abort the entire ingestion run.

#### Acceptance Criteria

1. WHEN a URL fetch fails, THE Pipeline SHALL log the error with the URL and continue processing the next URL
2. WHEN content extraction fails, THE Pipeline SHALL log the error with the URL and continue processing the next URL
3. WHEN embedding generation fails after retries, THE Pipeline SHALL log the error with the chunk preview and continue processing the next chunk
4. WHEN vector upsert fails after retries, THE Pipeline SHALL log the error with the vector ID and continue processing the next vector
5. WHEN the pipeline completes, THE Pipeline SHALL report counts of successful and failed operations per stage

### Requirement 11: Idempotency and Incremental Updates

**User Story:** As a knowledge engineer, I want to re-run the pipeline without duplicating vectors, so that I can refresh documentation without manual cleanup.

#### Acceptance Criteria

1. WHEN a vector ID already exists in Pinecone, THE Vector_Injector SHALL replace the existing vector with the new vector
2. THE Pipeline SHALL support an optional `--incremental` flag that skips URLs with unchanged content
3. WHERE incremental mode is enabled, THE Pipeline SHALL compute a content hash for each URL and compare against a local cache
4. WHEN a URL content hash matches the cache, THE Pipeline SHALL skip processing that URL
5. WHEN the pipeline completes in incremental mode, THE Pipeline SHALL update the local cache with new content hashes

### Requirement 12: Monitoring and Observability

**User Story:** As a knowledge engineer, I want detailed logs and metrics from pipeline execution, so that I can diagnose issues and optimize performance.

#### Acceptance Criteria

1. THE Pipeline SHALL log each stage transition with a timestamp
2. THE Pipeline SHALL log the count of items processed at each stage
3. THE Pipeline SHALL log the duration of each stage in seconds
4. WHEN errors occur, THE Pipeline SHALL log the error type, message, and context (URL, chunk index, etc.)
5. WHEN the pipeline completes, THE Pipeline SHALL output a summary report with total duration, success counts, and failure counts per stage

### Requirement 13: Content Quality Validation

**User Story:** As a knowledge engineer, I want the pipeline to validate extracted content quality, so that low-quality extractions don't pollute the knowledge base.

#### Acceptance Criteria

1. WHEN content is extracted, THE Semantic_Extractor SHALL validate that the Markdown content length is at least 100 characters
2. WHEN content is extracted, THE Semantic_Extractor SHALL validate that the content contains at least one Markdown heading
3. WHEN content validation fails, THE Semantic_Extractor SHALL log a warning with the URL and skip vector injection for that URL
4. THE Semantic_Extractor SHALL detect and skip pages that consist primarily of navigation links (more than 70% of content is links)
5. WHEN a page is skipped due to quality validation, THE Pipeline SHALL increment a "skipped_low_quality" counter in the summary report

### Requirement 14: Namespace Management

**User Story:** As a knowledge engineer, I want to list and manage Pinecone namespaces, so that I can audit and clean up the knowledge base.

#### Acceptance Criteria

1. THE Pipeline SHALL provide a `--list-namespaces` command that queries Pinecone and lists all namespaces with vector counts
2. THE Pipeline SHALL provide a `--delete-namespace` command that accepts a namespace name and deletes all vectors in that namespace
3. WHEN deleting a namespace, THE Pipeline SHALL prompt for confirmation before proceeding
4. THE Pipeline SHALL provide a `--dry-run` flag that simulates operations without making changes to Pinecone
5. WHEN dry-run mode is enabled, THE Pipeline SHALL log all operations that would be performed without executing them

### Requirement 15: Integration Testing

**User Story:** As a Training OS developer, I want integration tests that validate the pipeline against a sample sitemap, so that I can verify correctness before production deployment.

#### Acceptance Criteria

1. THE Pipeline SHALL include a test suite that processes a sample sitemap.xml with 5-10 URLs
2. THE test suite SHALL validate that all stages execute without errors
3. THE test suite SHALL validate that vectors are injected into a test namespace
4. THE test suite SHALL validate that metadata payloads contain all required fields
5. THE test suite SHALL validate that Aura DAP can retrieve vectors from the test namespace using a sample query
